## Header discrepancy and lossless conversion investigation

The original downloaded CSV header is already:

```csv
job,stage,machine,start,finish
```

The six-column header appears in the Library search's extracted sheet representation for the **same** file identity:

```csv
index,job,stage,machine,start,finish
```

That extracted representation is not the persisted CSV byte stream. The raw file has 600 five-field rows and no index column. The evidence packet retains the discrepancy in `evidence/header-discrepancy-search.json`. No separate raw six-column export was recovered in the filename searches, so **no six-to-five-column conversion was performed or claimed as verified**.

The lossless path for this actual artifact is identity: pass the original five-column bytes directly. The checker receipt retains those identical bytes in base64. Its captured JSON candidate was compared row-for-row against the original CSV: all 3,000 scheduling field values and the row order are unchanged.

Operation identity is `(job, stage)` under the original requirements. All 600 such pairs occur exactly once. The original row ordinal equals `20 * job + stage` for every row. An index defined by that formula would be redundant and recoverable from the existing fields, but the complete six-column display was not audited as an independently supplied raw file. Arbitrary extra index values should not be dropped on the strength of a header alone. A future six-column file would require its own byte identity, complete index verification, and byte-for-byte reconstruction check with retained index/format metadata.

For this run, no mathematical scheduling information was removed: no column or row was dropped, no value was repaired, and no candidate was re-sorted.
